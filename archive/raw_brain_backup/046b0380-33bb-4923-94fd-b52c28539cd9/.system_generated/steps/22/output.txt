In `llama.cpp`, partial GPU offloading—where a model is split between GPU VRAM and CPU system RAM—incurs a significant performance penalty because the inference process becomes bottlenecked by the relatively slow memory bandwidth of the system (DDR4/DDR5) compared to the extreme high-speed bandwidth of GPU VRAM.

### The Performance Penalty: The "Bandwidth Cliff"
*   **Memory Bandwidth Bottleneck:** Inference speed is generally dictated by how fast model weights can be moved into compute units. When parts of the model (or the KV cache) reside in system RAM, every token generated requires transferring data across the PCIe bus and through the CPU, which is orders of magnitude slower than VRAM[1][2].
*   **The "Cliff" Effect:** Many users experience a "bandwidth cliff" where adding even a few layers of CPU offload causes total tokens per second (TPS) to collapse[3][2]. Performance is not just incrementally slower; it often drops drastically as the bottleneck shifts from compute-bound (GPU) to memory-bound (System RAM)[1][4].
*   **Prompt Processing vs. Generation:** 
    *   **Prompt Processing (Prefill):** Highly parallelizable and benefits immensely from keeping as much as possible on the GPU[5][6].
    *   **Token Generation (Decode):** Sequential and latency-sensitive. This is where the penalty of offloading is most noticeable, as the system must wait for data from the slowest tier in the chain[6][7].

### Optimization Strategies (2025–2026)
To mitigate these penalties, advanced users in 2025 and 2026 employ several strategies beyond simple `–n-gpu-layers` settings:

*   **Targeted Tensor Offloading (`-ot` / `--override-tensor`):** Instead of using standard layer offloading, which can move entire transformer blocks (including KV cache) to the CPU, you can use the `-ot` flag to offload only specific, non-latency-critical sub-layers (like certain FFN experts in MoE models) while keeping attention and KV cache on the GPU[8][9]. This keeps the "hot path" in VRAM and reduces PCIe traffic[10][9].
*   **KV Cache Management:** The KV cache is a major "VRAM eater." If your cache spills into system RAM, performance tanks. Ensure you have enough VRAM headroom for the context size you are using, or reduce the context window to keep the cache entirely on the GPU[1][3].
*   **"Always Active" Priority:** For Mixture-of-Experts (MoE) models, prioritize offloading "always active" parameters (Attention and Shared FFN layers) to the GPU, while offloading routed expert layers to the CPU[8][11].
*   **Batch Size Tuning:** Adjusting the physical micro-batch size (`-ub`) can help optimize throughput. Larger batch sizes can improve prompt processing speed, though they require more VRAM, forcing you to move more layers to the CPU—a trade-off you must balance based on your specific workload[5].
*   **Automated Allocation:** Newer versions of `llama.cpp` include automation features that perform virtual test allocations to help fit models across multiple GPUs or mixed GPU/CPU setups more efficiently than manual guessing[12][13].

### Summary Recommendation
*   **Avoid the "Spill":** If possible, use smaller quantization (e.g., Q4_K_M) to fit the *entire* model into VRAM rather than running a larger, higher-precision model that requires partial CPU offload[3][14]. 
*   **Benchmark:** Use `llama-bench` to test your specific hardware configuration. Because the bottleneck is often the memory bus, your specific CPU, RAM speed (DDR4 vs DDR5), and PCIe generation will significantly change how much of a penalty you experience[5][1][7].
